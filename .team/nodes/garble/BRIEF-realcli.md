两条预测被推翻，都已如实记：**C**（只打一行不能自愈，必须整帧重绘）、**E**（600ms 快切在该假 TUI 上不错排）。

❌ **还差的**：那是 `grok-tui.c` 一个**我们自己写的假 TUI**。
用户看到坏的是 **真 Agent CLI**。⛔ 不能拿假 TUI 的结论直接去改产品。

## 1. 本格要回答的**唯一**问题

> **真 Agent CLI 在被挤窄之后，会不会自己整帧重绘？**

- **会** ⇒ 上一格的机制**解释不了**用户那 5 个「一打开就坏」⇒ 如实写「机制在真 CLI 上不复现」，
  本条线索到此为止，⛔ 不许硬套。**这是有效交付。**
- **不会（或很慢 / 只在有输入时才绘）** ⇒ 机制成立，修法就此定下（见 §4）。

## 2. 台子（⛔ 全部自建，一个字都不碰用户的）

照抄上一格 `.team/nodes/garble/run-cause.mjs` 的起法：
独立 `TMUX_TMPDIR` + 独立 socket + 自建 daemon 换一个端口（⛔ 端口被占换一个，不 kill 占用者）。
⛔ **不连 `:9900`；⛔ 不扫 `/tmp/tmux-501/`。** 收工只 `kill-server` 自己那颗 socket。

**在自己这颗 tmux 里跑真 CLI。** 首选 `cursor-agent`（用户那 5 个坏会话就是这一类席位）；
拿不到就退 `claude`，并写明换了哪个、为什么。

🔴 **⛔ 不要给它发任何 prompt / 不要触发模型调用**（省额度，也不需要）——
只要它把 TUI 首屏画出来就够了。**在自己起的 pane 上 `send-keys` 是允许的**
（红线针对的是用户的 pane），但本格只在臂 B′ 用一次。

## 3. 要跑的矩阵（🔴 少一臂不算做完）

pane 起 **235x50**，等真 CLI 首屏画完并静默。判绿口径 = **与「同一 CLI 在 157x47 下从头画出来的首屏」逐字节一致**
（做法同上一格的 `want157`：另起一个控制 pane 直接以 157x47 跑同一个 CLI）。

| 臂 | 做法 | 事前预测 |
|---|---|---|
| **A′** | 订阅 157 挤窄，**不做任何输入**，等 3s 抓 | **红** |
| **A″** | 同 A′，但等 **30s** 再抓 | **红**（若转绿 ⇒ 它只是重绘得慢，把实测秒数写出来） |
| **B′** | 订阅 157 挤窄后，`send-keys` 一个**无副作用**的按键（如方向键）促其重绘，再抓 | 绿 |
| **D′** | 订阅 **235**（不挤窄） | **绿** |

🔴 另记一个关键读数：**挤窄之后、抓快照之前，该 pane 有没有产生新字节**
（`capture-pane` 指纹在 reshape 后是否变化 + 变化耗时）。这是区分「不重绘」与「重绘慢」的量。

## 4. 反推与修法选型（⛔ 本格仍然不修）

已定位的产品侧发出点（上一格给的，本格核对一遍是否仍然如此）：

- `src/components/terminal/TerminalPane.jsx:101` — `subscribe(target, act.rows, act.cols)`，`act` 来自 fit / `SameWidthController.settle`
- `src/vendor/agentmirror/client.js:123` — 把该 rows/cols 送进 `subscribe` 帧

**本格要在产物里给出三个候选修法的证据支持度，⛔ 不许只推荐不给证据：**

| 候选 | 代价 | 本格哪个读数支持/反对它 |
|---|---|---|
| ① 订阅改发**主机几何**，客户端自己想办法显示 235 列 | 显示层要改（字号/横向滚动），是产品决策 | D′ |
| ② 仍挤窄，但**等到应用重绘完成**再上屏 | 首屏变慢（假 TUI 上 367ms，真 CLI 待测） | B′ / A″ 的秒数 |
| ③ 挤窄后**主动促其重绘** | 需要向 pane 发按键 = 副作用，风险高 | B′ |

⛔ **不许在本格实现任何一个。** 只给证据 + 事前预测「修完哪一臂应由红转绿」。
